## 2026-10-03 · `#271` `fetch_community_events` 三处输出缺陷根治：VRC Search 过 Cloudflare / RLVRC 时区归位 / limit 不再挤掉未来（@nixi-agent）

- `#271` (MERGED, 2026-10-03 21:58 UTC+8, @nixi-agent) fix(events): VRC Search 走 core 有头浏览器过 Cloudflare；RLVRC 时区按北京时间；limit 截断未来优先 —— 分支 `fix/events-vrcsearch-browser-tz-limit`，3 commits（`ed08c28` 主体 → `e2ead41` 审查 ⚠️1+💡2 → `bed1832` 审查 W1），merge `0e3190a`
- 需求来源：使用者调研"最近 VRChat 社区有什么活动"时，由 Agent 实测发现 `fetch_community_events` 三处输出缺陷，使用者要求修复
- 缺陷 1 **VRC Search 源长期全灭**：`sourceBreakdown.vrcsearch` 恒为 `ok:0 / fail:56` —— 根因实测确认 `search.vrcwwt.com` 被 **Cloudflare JS 挑战**保护，裸 HTTP（含浏览器 UA、curl）一律 403，真实浏览器进入后 5~8s 自动放行；原实现 56 次裸请求不但全失败，还各自等一次超时（单轮采集 200s+）
- 缺陷 2 **RLVRC 时间晚 8 小时**：`api.rlvrc.cn` 返回**北京时间且不带时区标记**（`week:"星期六"` + `time:"2026-10-03 21:00"`），原实现把"无时区"一律当 UTC ⇒ `start_bj`/`start_local` 全 +8h（实例："猜歌交流夜"真实 10-03 21:00 被显示成 10-04 05:00）
- 缺陷 3 **limit 截断挤掉未来**：窗口内常有 1300+ 场、排序主键是群组人数与时间无关，`slice(0, limit)` 直接按现有顺序截断 ⇒ `limit=300` 实测只返回到 10-02，未来整段消失
- 架构决定：**浏览器能力只进 core，插件保持零依赖** —— 新增 `core/browser-fetch.js`（285 行，`browserFetchMany` 一次性拉起 headful 浏览器顺序访问全部 URL）并注册为 `web.browserFetchMany`（`serviceOwners='core'`）；插件侧只做 `api.hasService()` 探测 + `api.consume()`，遵守 `docs/PLUGIN-DEV.md §8`（插件禁 import `core/`、禁 `child_process`）
- 关键设计：单页失败只影响该页、整批不可用也不 throw（结构化降级）；通道不可用 → 该源整体 `not_queried` + **一行日志**，绝不再逐 URL 发裸请求；代理默认直连、首页 `ERR_PROXY_CONNECTION_FAILED` 时关浏览器直连重建；headful 是过挑战前提（headless 被硬拒），无显示器 / 无浏览器 / 无 playwright 的环境自动降级、其余源与全部工具不受影响；纯函数抽到 `plugins/official/events/lib.js`（153 行）供 `node --test` 直接断言生产同一份代码；**不改 `start` 字段本身**（DB `start_iso` 靠它做字符串区间比较，追加 `+08:00` 会破坏比较）
- 验证：新增单测 17 → 21 例 + `test/browser-fetch-config.test.mjs` 5 例；全量 357 → 374 → 378 → **383/383 全绿**；真实 Cloudflare 链路 **56/56 页、67090ms**、`vrcsearch {count:651, ok:56, fail:0}`（改造前 0/56）；部署后经 MCP 实调 `limit=20` 返回的 20 条**全部未开始/进行中**；时区 `start:"2026-10-03T21:00"` → `start_local = start_bj = "10-03 21:00"`、`tz_label="北京时间"`；隔离实例不注册服务 → 整源跳过、整单 2384ms
- 审查：两轮 —— 首轮 `psenY`（无阻断 + ⚠️1 脏串时区列静默变空 + 💡2 无 single-flight 致并发各起一个有头浏览器）；次轮 `EMeowAGENT` **APPROVED**（已独立实测 chrome 通道真实抓取）另给 W1（`VRC_MONITOR_BROWSER_FETCH_TIMEOUT_MS` 负值穿透 ⇒ 实测 env=-5 时 613ms 即 `deadline_exceeded`）与 2 条 💡；三条全部落实并各附故障注入 / 复现实测

**演进意义**：① **"插件零依赖"与"需要真浏览器"的冲突，解法是把能力上收到 core 作为服务注册，而不是让插件变重**：过 Cloudflare 挑战必须真浏览器（headful），但插件不能引 playwright —— 于是新增 core 能力 `web.browserFetchMany` 走服务注册表（§1.1 允许的"底盘演进"），插件只探测 + 消费。这条边界一旦立住，后续任何"插件需要重能力"的需求都有了固定落点，而不是每次破例。② **"探测失败回退、失败不抛错、逐分支留痕"从本机增强模式一路复用到浏览器通道**：整批不可用返回结构化 `not_queried + reason` 而非 throw，跨平台（无头 Linux / NAS / 群晖）自动降级且不影响其它源 —— 与 08-10 确立的"探测式回退"是同一模式，此处是它在**外部依赖不可控**场景上的第二次实体化。③ **"无时区串一律当 UTC"是一类系统性错误**：RLVRC 用北京时间且不带标记，+8h 漂移静默发生了很久；修复不只调 +8，而是把"源 → 基准偏移"抽成显式函数 `naiveBaseOffsetH(src)`，且**不动 `start` 字段**（避免破坏 DB 字符串区间比较）—— 又一次"数据表示与展示换算必须分层"。④ **排序主键与截断语义解耦**：`selectWithinLimit` 让"不该被砍的（未开始 / 进行中）先留、不足额才用最近的过去事件补齐"，而不是依赖"排序恰好按时间"这种偶然前提；`start` 缺失的活动按"未开始"保留、不静默丢弃。⑤ 审查方从 `psenY` 换到 `EMeowAGENT` 并给出 APPROVED + W1 负值穿透实测 —— **"配置项非正数回落默认"这类朴素护栏，正是靠复现实验才被发现的**，与本项目"逐分支留痕 / 禁静默降级"的日志哲学同源。
