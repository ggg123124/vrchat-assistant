**演进意义**：① **「加索引」不是性能问题的通用解，谓词形状决定执行计划**：213.7ms 里没有一行慢代码，一句 `EXPLAIN` 的 `SCAN e` 就说明全部——`NOT (A AND B)` 叠加逐行 `json_extract` 让优化器彻底放弃索引。作者把五种「看起来更聪明」的写法逐个实测全灭，共同点是**索引列与 JSON 判定同处一条语句**；真正的解法是把判定**物化**成生成列，再让两条 COUNT 各自走索引。**先让谓词变成优化器认识的东西，索引才有机会被用上**——与 10-19 `#311`「超时不是孤立常量，而是一条链上的约束」同族：性能改动的第一性问题不是「哪里慢」，而是「计划为什么没被选中」。② **基准规模决定量级声称，PR 数字与使用者体感是两件事**：PR 在 62k 行上报 213.7→9.0ms（23.7×、建索引 460ms），审核在生产副本 832,220 行（13 倍）上实测 1.1–6.5s → 75–374ms（3–18×）、建索引 4,946ms。方向与语义都成立，但**倍数与一次性成本都差一个量级**——性能类 PR 的改前/改后必须在生产规模上再跑一遍，否则记录里的数字会变成另一种漂移（与使用者的实际体感不一致）。③ **「降级回全表扫描」是文案里的谎，比没有降级更坏**：`ALTER` 在 `try` 外（低版本直接崩），`catch { total = 0 }` 是把 total **置 0** 而不是回落旧查询，而注释与日志写的是「计数将回落到全表扫描」。**声称存在安全网会让后来者不去查它**；降级要么真的实现并逐分支留痕，要么别在文案里许诺——这与仓库既有纪律「兜底/降级路径必须逐分支打日志、禁静默降级」是同一条，只是这次的静默发生在文档里。④ **等价性用例必须穿过被测代码的真实入口**：作者初版用例「自己重放两条 SQL 做对比」，把实现改回旧条件**依然全绿**——它钉的是脑子里的 SQL，不是仓库里的代码；改成调用真实 `dashboard.events` service 后变异才咬得动（删索引 ⇒ 1 failed / 5 passed）。这是 2026-10-22 `#314`「消费点必须单独设断言」、10-18 `#305` 同一条纪律的第三次固化：**判据与被测路径之间不能隔着一层复述**。⑤ **「按字符串形状分派」是隐性缺陷源**：`conds.filter(c => !c.includes('json_extract'))` 用 SQL 子串判断「这条条件是不是 JSON 判定」，将来任何含该子串的筛选会被静默从两条子查询里剔除 ⇒ total 偏大且没有用例会红；审核建议给 conds 带类型标记。**当一段逻辑靠「字符串里有没有某个词」来分类时，它已经与生成这段字符串的人耦合了**——这类耦合不会报错，只会在某次无关的新筛选上线后让数字慢慢偏。⑥ **Schema 演进有两个独立要修的面：迁移判据与投影**：`PRAGMA table_info` 不返回生成列 ⇒ 判存在永远为假、第二次 init 崩；`SELECT e.*` 会把生成列带进 DTO ⇒ 必须显式列。**加一列需要的不是一条 ALTER，而是「怎么判断它已经存在」和「怎么不让它意外出现在返回值里」两处同步修改**——前者关系迁移幂等，后者关系对外契约。⑦ **被拒绝的建议也要有归宿**：日期路径 +24%~+52% 的回归，作者未采纳门控，审核方明确标「非阻断、记录在案由维护者取舍」，并同时补用例钉住等价性。**取舍可以不做，但不能不说**——与 10-27 记的「非阻断建议的归宿只能是文档」是同一条，区别在于这次连「为什么不修」的判断依据（区间越宽越亏的实测表）都留在了 PR 里。
