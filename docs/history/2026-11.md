**演进意义**：① **「加索引」不是性能问题的通用解，谓词形状决定执行计划**：213.7ms 里没有一行慢代码，一句 `EXPLAIN` 的 `SCAN e` 就说明全部——`NOT (A AND B)` 叠加逐行 `json_extract` 让优化器彻底放弃索引。作者把五种「看起来更聪明」的写法逐个实测全灭，共同点是**索引列与 JSON 判定同处一条语句**；真正的解法是把判定**物化**成生成列，再让两条 COUNT 各自走索引。**先让谓词变成优化器认识的东西，索引才有机会被用上**——与 10-19 `#311`「超时不是孤立常量，而是一条链上的约束」同族：性能改动的第一性问题不是「哪里慢」，而是「计划为什么没被选中」。② **基准规模决定量级声称，PR 数字与使用者体感是两件事**：PR 在 62k 行上报 213.7→9.0ms（23.7×、建索引 460ms），审核在生产副本 832,220 行（13 倍）上实测 1.1–6.5s → 75–374ms（3–18×）、建索引 4,946ms。方向与语义都成立，但**倍数与一次性成本都差一个量级**——性能类 PR 的改前/改后必须在生产规模上再跑一遍，否则记录里的数字会变成另一种漂移（与使用者的实际体感不一致）。③ **「降级回全表扫描」是文案里的谎，比没有降级更坏**：`ALTER` 在 `try` 外（低版本直接崩），`catch { total = 0 }` 是把 total **置 0** 而不是回落旧查询，而注释与日志写的是「计数将回落到全表扫描」。**声称存在安全网会让后来者不去查它**；降级要么真的实现并逐分支留痕，要么别在文案里许诺——这与仓库既有纪律「兜底/降级路径必须逐分支打日志、禁静默降级」是同一条，只是这次的静默发生在文档里。④ **等价性用例必须穿过被测代码的真实入口**：作者初版用例「自己重放两条 SQL 做对比」，把实现改回旧条件**依然全绿**——它钉的是脑子里的 SQL，不是仓库里的代码；改成调用真实 `dashboard.events` service 后变异才咬得动（删索引 ⇒ 1 failed / 5 passed）。这是 2026-10-22 `#314`「消费点必须单独设断言」、10-18 `#305` 同一条纪律的第三次固化：**判据与被测路径之间不能隔着一层复述**。⑤ **「按字符串形状分派」是隐性缺陷源**：`conds.filter(c => !c.includes('json_extract'))` 用 SQL 子串判断「这条条件是不是 JSON 判定」，将来任何含该子串的筛选会被静默从两条子查询里剔除 ⇒ total 偏大且没有用例会红；审核建议给 conds 带类型标记。**当一段逻辑靠「字符串里有没有某个词」来分类时，它已经与生成这段字符串的人耦合了**——这类耦合不会报错，只会在某次无关的新筛选上线后让数字慢慢偏。⑥ **Schema 演进有两个独立要修的面：迁移判据与投影**：`PRAGMA table_info` 不返回生成列 ⇒ 判存在永远为假、第二次 init 崩；`SELECT e.*` 会把生成列带进 DTO ⇒ 必须显式列。**加一列需要的不是一条 ALTER，而是「怎么判断它已经存在」和「怎么不让它意外出现在返回值里」两处同步修改**——前者关系迁移幂等，后者关系对外契约。⑦ **被拒绝的建议也要有归宿**：日期路径 +24%~+52% 的回归，作者未采纳门控，审核方明确标「非阻断、记录在案由维护者取舍」，并同时补用例钉住等价性。**取舍可以不做，但不能不说**——与 10-27 记的「非阻断建议的归宿只能是文档」是同一条，区别在于这次连「为什么不修」的判断依据（区间越宽越亏的实测表）都留在了 PR 里。

② **同一个谓词在两处各写一遍，就一定会打架**：`isWebOnline` 判「这人在游戏里、不是网页在线」（PR 自己的用例这么断言），`groupByWorld` 却把他挂进「网页端在线」组。两处没有共享判据，只能靠注释互相许愿——作者甚至在 `groupByWorld` 里写了「其余（无 worldId）→ 只可能是网页/移动端在线，**不该走到这里**」，而这条「不该」正是可达路径。三方审核用同一份输入各自复现出同一矛盾，说明它不是边界情况而是结构性冲突；更隐蔽的后果是**同一区块里标题与行文案互相打脸**（标题「离线」，同一人的 `statusText` 是「在线」）。当一个判断同时决定「分组归属」与「行内文案」时，它只能有一处实现。

③ **修好一个桶 ≠ 修好一类缺陷**：`none` 桶改「位置未知」后，`offline` / `offline:offline` 桶原样继承了同一条矛盾，只是桶的名字换了。缺陷的形状是「所有可达桶都要枚举一遍」（none / offline / offline:offline / traveling / private / local / friends / group），而修复的形状是「改我想到的那一个」。这类修复只有把分支表列出来逐条给期望值才算完成——**修缺陷要枚举全部入口，不是只修掉复现路径**，与 2026-10-22 `#314`「消费点必须单独设断言」是同一纪律的又一次显形。

④ **「已修」是断言，必须能被 diff 钉住**：作者两次自报已修（`.wg-label`、`instanceKeyOf`），实际改动落在自己 fork 的 main 上，PR 分支四个提交里那两处代码一字未动；两次都是审核方逐 commit `git show <sha>:<file>` 才发现的。多人协作里，**「我说改了」与「分支上改了」是两件事，而全绿的测试对两者一视同仁**——复验因此必须落到「改动的对象是不是这条分支上的这个文件、这个提交」，而不是「作者说改了 + CI 绿了」。这条与 11-02 `#317` 的「PR 数字 vs 生产体感」同族：**自报的完成状态和实测的完成状态之间，隔着一层需要被独立穿透的边界**。

⑤ **护栏要能证明「修复前会红」**：`not.toContain('离线')` 在旧代码上同样成立（旧代码给的是「网页在线」），于是删掉半个修复条件该文件仍 14/14 全绿——用例名写着「堵住 offline:offline」，实际什么也没堵。改成精确值 + 不重复之后，变异实验才咬得住（删条件 ⇒ 作者用例 + 审核方探针同时变红）。**一条从没红过的用例不是护栏，是装饰**；判据不是「它现在绿」，而是「我能让它红」。这是 11-02 `#317`「等价性用例必须穿过真实入口」的下一步：穿过真实入口之后，还要穿过**取值空间**——断言必须落在「只有修好了才对」的那个值上，而不是「修好之后恰好不出现」的任意特征。

⑥ **按序号的 CSS 选择器是结构耦合**：`.wg-head span:nth-child(2)` 在有缩略图时恰好命中标题，而本 PR 新引入的形态（无名世界 ⇒ 无缩略图 + 新增沙漏图标）让标题变成第 1 个元素子节点 ⇒ 规则一个 span 都命中不到，41 字符 ID 在 248px 侧栏折成 3 行、把一个分组头部撑到接近成员卡片两倍高。**序号是「渲染顺序」的断言，class 是「语义角色」的断言**；前者会在任何一次模板微调后静默失效，而且失效方向恰好是「新加的形态最丑」——因为新形态往往正是打破原有子节点顺序的那个。同一类耦合在 JS 里也有对应物（11-02 `#317` 用 `conds.includes('json_extract')` 按字符串分派）：**凡是「按位置/按形状」而不是「按身份」选中的东西，都会在下一次无关改动后悄悄错位**。

⑦ **同一逻辑的第二份实现与文档，是下一个 agent 的抄写源**：新口径只落在 `ui/src`，legacy `client/js/util.js` 的 `worldLabel()` 与 `skills/plugin-first-web-dashboard/references/remote-vrchat-dashboard.md` 仍钉着「未公开位置」，`test/dashboard-util.test.mjs` 还明确断言这两句（根套件为此保持全绿）。默认走新 UI 时这些都不影响用户，但**文档与旧断言会以「权威」的身份，把刚清掉的词原样带回来**——审核方把它记为 💡 而非 🔴 是对的（不阻断合并），但它决定了这个 PR 的寿命：同一仓库里存在两套同名 API、行为相反，下一次照文档实现的 agent 会合理地写回旧文案。这也解释了为什么「文档同步」在 DEVELOPMENT.md 里是硬性条目而非建议。

⑧ **对齐既有权威实现比自创标签便宜，也更不容易错**：作者没有重新设计一套「未知」词表，而是读 VRCX 的 `getLocationText` / `isRealInstance`，照抄两条规则（有 worldId 就显示名字或 ID、从不生成「未知/未公开」；`offline` / `private` / `traveling` / `local` 不算真实实例）。结果是同一个词在三个审核方那里几乎没有分歧——**当同一份数据已经被一个成熟客户端渲染多年，口径就是它，而不是我们的直觉**；「未公开位置」被用户当成 bug 而不是「保守的默认值」，正说明它偏离的不是审美，而是这个领域里已经被确立的事实表达方式。

⑨ **同一个数据源被两个视图渲染，就必然有第二个消费点等着漏**：`RightBar`（侧栏）与 `FriendsView`（好友页）吃的是**同一份** `groupByWorld()` 输出，作者在 `RightBar` 补了 `locFrom` 就以为收口，好友页仍传 `g.list[0].location`——表现是「侧栏点开是那间房，好友页点开是英文 `offline` 弹窗，还向 `/api/dashboard/instance?location=offline` 发一次注定无效的请求」。这是 ③「修好一个桶 ≠ 修好一类缺陷」在**消费点维度**的同一条：分支表要枚举，**渲染同一份派生数据的视图也要枚举**；而枚举的依据不是记忆，是 `grep` 出所有 `groupByWorld()` 的调用方。审核方给的是「哪个函数返回什么、标题落到哪个字符串、请求打到哪个 URL」的链路，不是「这里看着不对」——**只有能给出链路的问题描述，才可能被作者复核为「成立」而不是「你觉得」**。

⑩ **同一个 PR 里扩了能力、没扩判据，就会长出「有的人有、有的人没有」**：本 PR 自己刚让 `parseLoc` 剥掉 `traveling:` 前缀、`locLabelFull` 能把传送中的世界渲染成「公开 · 1」，而 `locSource` 仍用 `loc.startsWith('wrld_')` 选源 ⇒ 组内全是「传送中」成员时组头 chip 空白，成员卡片却有房间号。修法不是给前缀打补丁，而是把判据改成**语义判据**「`parseLoc(loc).instanceId` 非空即算可用」。这与 ⑥ 是同一族（按形状 vs 按身份）：**能力升级时，所有「字符串长什么样」的旁路判据都要同步复审**，否则新能力只在一半路径上生效。

⑪ **护栏必须守卫到「被测层之外的那一层」**：`locFrom` 的不变式在 composable 层有完整用例、全绿；可 `FriendsView.vue:138` 把它退回 `g.list[0].location` 时，186 条测试一条都不红——因为**没有任何用例碰过模板里那个实参**。补的 `view-loc-from.test.js` 读 `.vue` 源码断言 chip 的 `openInstance` 实参必须含 `locFrom`（沿用 `seq-guard.test.js` / `template-bindings.test.js` 的既有手法），变异自证后能精确咬住。但写这条护栏时先踩了假阳性：`FriendsView` 里 3 个 `.fg-loc` 有两个是「我自己所在房间」、直接读 `store.me.location`，**语义上就没有「显示与点击不同源」这回事**，第一版把它们也算成违规 ⇒ 扫描式护栏必须先区分「形状像」与「语义同」，否则第一条用例就误伤自己；解析用引号配对而非 `[^>]*`，也是因为该仓库已经被箭头函数的 `>` 截断踩过两次。**「这一层没有断言」与「这一层不会错」是两件事**——而补断言的动作本身，需要先想清楚「这条真的该守吗」。

**演进意义**：

① **「抓到了」与「读懂了」是两个指标，而成功计数器只数前者**：`okCount++` 的判据是「2xx + 有 body」，于是 56 个页面全部改版成另一种 DOM 时，指标是 `ok:56 / fail:0`——**完美健康**。整个故障里唯一说出真相的是作者自己手写的那条 `56/56 页可取但 0 命中` 警告：他早就怀疑过「页面取回 ≠ 解析出东西」，只是这个怀疑没有变成指标。**健康度计数必须包含「产出」，否则『目标站点改版』这种最普通、也最必然发生的故障，会长期伪装成全绿**——审核建议给 `sourceBreakdown` 加 `parsed` 计数、或 `ok>0 && count==0` 打 WARN，正是把这条人工警告升级成系统判据。这与 2026-10-22 `#314`「消费点必须单独设断言」同族，只是这次被漏掉的「消费点」是**监控自身的产出**。

② **报障里「顺带发现」的那一节，比主故障更危险**：issue 的时间口径分析具体到机制（「本地 naive 被当 UTC 存储 ⇒ 固定 8 小时偏移」），读起来完全自洽，而它指向的修法是「补 `+8` 归一化」——照做会直接打红既有的 21 条防回归用例，并让整条时间轴偏 8 小时。两份独立审核各自用「`naiveBaseOffsetH(VRC Search) === 0`」+「真站 `ec-start` 与 `data-starts` 的 HH:MM 20/20 一致」把它推翻。**报障者的主故障通常被反复验证过，而「顺便发现」往往是凭印象补的因果**；它危险恰恰因为夹杂在正确内容里、共享同一份可信度。这与 2026-10-27 `#316` 记录「根因描述里夹带的错误前提会决定修复范围」是同一条的第二例——**任何能改变修复方向的断言，都必须自带一条可执行的判据（用例、`grep`、或一次真站测量）**，否则它只是修辞。

③ **当「格式」是主键的一部分，格式迁移就是数据迁移**：`PRIMARY KEY (source, name, start_iso)` 让「把时间统一成 ISO」这个看起来纯格式化的动作，变成了「同一条活动会以新旧两个主键并存、跨源去重键 `normName|start` 同时失效」。审核在 issue 阶段就把它列为 ⚠️，PR 因此没有停在「重写解析器」，而是把 `cleanupLegacyVrcSearchRows()` 写成了实现的一部分。**只要一个字段参与唯一性判据，它的格式就是一种持久化契约**——改契约可以，但迁移语句必须与解析器同批上线，否则「修好数据源」的直接后果是「数据重复」。

④ **迁移必须自带「凭什么可以执行」的判据，而这里选错了判据**：清理只在 `okCount > 0 && opened.length > 0` 时跑，即「至少 1 页命中」——但审核实测 `/zh/events/music/next-week/` 无 consent cookie 时**返回 200 且 0 张 `event-card`**，`okCount` 只能证明「取回」不能证明「解析覆盖」。极端情况下「1 页命中」就会一次性删掉全部旧行。审核给了两条替代（`okCount === targets.length`、或改用一次性迁移标记），PR 未采纳（非阻断）。这条值得单独记：**删除型语句的准入条件，要用「覆盖了多少」而不是「成功了多少」来表达**——与 ① 是同一个计数语义缺陷的第二次显形，区别是这次它握着一把 DELETE。

⑤ **纯函数是单测的前提，不是重构的副产品**：解析器原先坐在 `index.js` 的插件闭包里、没有导出，审核因此明确指出「要按建议补单测，**必须先把解析器抽成零依赖模块**」。PR 把 `parseVrcSearchCards` 连同 `decodeEntities` / `stripHtml` / `CAT_ZH` 一起迁进 `lib.js`，于是「喂真站夹具、断言解析出 1 条、断言 `start` 带不带 `Z`」才成为可能。**「这个函数测不了」几乎总是「这个函数的边界没画对」**——把 IO 与纯逻辑分开不是为了分层好看，是为了让断言有落脚点；而顺带合并两份 `CAT_ZH` 映射，则是同一动作的副作用收益（改一处 vs 改两处）。

⑥ **真站夹具比自造 HTML 值钱，因为解析器的风险不在语法而在对方改版**：`test/fixtures/vrcsearch-events.html` 存的是真站 2 张卡片原样；审核更进一步，用三语页面共 **43 张真卡片**直接跑 PR head 的生产解析器（20/18/5 全中）。自造 HTML 只能证明「代码符合自己的想象」，真站夹具则是「上次长什么样」的唯一物证——它既能让今天的解析器回归，也能在下次改版时**立刻指出新结构变了哪些字段**。这是 VRC Search 第二次因上游改版整体失效（本次），夹具是唯一能让第三次变便宜的东西。

**演进意义**：

① **「同一世界」不是「同一场次」，而一行无条件赋值把两者混为一谈**：`curStart = dt` 写在 `wrld_` 分支的末尾，从缩进看它属于「记录当前位置」，从语义看它却是「重置会话起点」——只要你还在同一个世界再来一条位置事件（心跳、换实例、重连），起点就被推后。136 分钟的场次于是被压成 2 分钟，**再被 `<3 分钟` 阈值过滤，从「算少了」升级成「这件事没发生过」**。这是 2026-10-26 记录「阈值过滤会把算少了升级成没发生过」那条链的终点，也说明**阈值不是缺陷的放大器，而是缺陷的隐形器**：它把「数字偏小」这种可被察觉的异常，转成了「世界列表里少一行」这种无从察觉的缺失。

② **缺陷在统计层，修复就必须在统计层——上游的「重复」是设计，不是脏数据**：最顺手的修法是「把 300s 去重窗口放大」，而 10-27 的复核已经用一条用例名把它挡回去了：「窗口外的同实例重复**仍落一条心跳**」——每条心跳都是活跃度证据，放大窗口会吞掉真实数据。PR 因此只动 `curWorld !== wid` 一行。这是本仓库第三次出现同一形状（2026-10-22 `#315` 去标识化判据、11-02 `#317` 生产规模基准）：**判断「这是缺陷还是设计」的唯一依据是「有没有一条用例在要求它出现」，而不是「输出长得像不像脏数据」**；修错了层，缺陷会以另一种形态原样存活。

③ **修复会把一类错误换成另一类，取舍要写进代码而不是留给下一个人重新推理**：修好之后，崩溃/重启期间没有 offline 行的两段会被合并成一场、可能偏长——从「少算成 0」变成「可能多算」。此时最顺手的动作是加「间隔 N 分钟就切分」的阈值，而它会砍碎真实的长场次（VRChat 静止时不发事件 ⇒ 长场次天然就是稀疏的、跨度大的）。PR 明确**不加阈值**，并把理由与已知限制写进 `social.js:482-487` 注释。**「加个阈值」是处理时间序列问题时最顺手的错误答案**：它能让症状消失，同时制造一个更难发现的症状；接受「可能偏长」而不是「再加一个参数」，是把取舍放在代码里，而不是留给下一个读注释的人自己猜。

④ **只有「在旧代码上会红」的用例才算护栏，而对照组必须由审核方自己搭**：5 条新用例在基线 `64d6a4a` 上 **1 pass / 4 fail**、在 head 上 5 pass——这证明它们咬住了缺陷；但审核没有停在这里，而是**另写 5 个不复用 PR 用例的场景**做矩阵（head 5/5、基线 2/5），其中「A→traveling→A 仍是两场」与「1 分钟短场仍被过滤」分别证明「正常的换世界切分没被改坏」与「阈值语义没被顺带改掉」。这是 2026-11-17 `#319` ⑤「一条从没红过的用例不是护栏，是装饰」的下一步：**作者自证「新用例会红」之外，还要有人用不同的输入独立证明「修复的边界没被扩大」**——前者证明修对了，后者证明没修过头。

⑤ **修好一个数字，会改掉另一个数字的口径**：`visits` 的旧实现把每条同世界心跳都切成一次新会话（次数被心跳抬高），修复后按连续 worldId 段计 ⇒ 周报 UI 的「N 次」会明显变小。方向更正确，但**使用者看到的是「我的到访次数怎么少了」**——这类「修复的正确性表现为另一个指标变大或变小」的改动，是下一轮 bug 报告的最佳素材。审核因此把它列为非阻断并要求写进口径说明。本记录承担这件事：**周报「到访次数」= 连续同世界段数，不是位置事件条数**；旧值偏高是缺陷的副作用，不是基线。**口径必须与修复同批落地，否则修复会在两周后被当成回归回滚。**

⑥ **「已知缺陷 → 双复核 → 修复」的记录链，在修复发生时兑现价值**：10-26 首次记录（当时无 PR、明确标注未修）、10-27 两位参与方独立复现并把「采集层漏了去重」这条错误根因改掉、同时预告了镜像面、11-26 PR 落地时正文直接引用这些结论（「两份审核均实测复现，并确认修复位置在统计层、不要改上游 300s 去重」）而不是从零论证。**演进记录真正的用处不是历史归档，而是让下一次修复不必重新推导一遍取舍**——本条的 ③（不加阈值）与 ⑤（visits 口径变化）如果不是写在文档里，三个月后拿到「周报时长偏大 / 到访次数变少」报障的人，会把它们各自「修」回原样。
