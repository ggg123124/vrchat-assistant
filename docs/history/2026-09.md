## 2026-09-01 · rateLimiter 挂死根治：socket 超时 + 队列任务级超时（PR #117）

- `#117` (MERGED, 2026-09-01) fix(api): 加 socket 超时 + 队列任务级超时，防止挂死请求锁死 rateLimiter（64d34ec，@nixi-agent）
- 现象：get_prints 等走 rateLimiter 的 API 工具调用后 420s 超时无响应，但直连 VRChat API 1.7s 秒回；/health 显示 queueLength≈50（上限）且 isProcessing=true 长期不释放
- 根因：vrchat-api.js 的 5 处 https.request（_requestRaw/_basicAuthRequest/_rawRequest/upload/download）均无超时保护——网络抖动时 socket 可永挂不返回也不触发 error；被 rateLimiter 包住的请求占住队头后 `_processing=true` 永不释放，后续所有请求排队干等、集体卡超时
- 修复①治本：5 处 https.request 全部加 `req.setTimeout(REQUEST_TIMEOUT_MS=15000, () => req.destroy(new Error(...)))`——超时 destroy 触发 error → reject，把挂死请求踢出队列
- 修复②防御：core/rate-limiter.js 新增 taskTimeoutMs（默认 30000），_processQueue 内 Promise.race 包住 item.fn()——即使 handler 内部死等也会被强制超时（评审修复 37f795c 进一步做 per-task 超时覆盖 + 聚合 handler 隔离，回应评审 ⚠️1/⚠️2/💡1）
- 关联：issue #118（CLOSED，2026-09-01，由 #119 根治关闭）events 插件启动后自动采集/深挖上千群组持续占满 rateLimiter 队列——#117 修的"挂死锁死队列"与 #118 的"正常请求被大量采集挤占"是同一队列治理问题的两个面，后者已由 #119（删预热钩 + 群组缓存优先 + 每日离线刷新）解决，见下方 #119 条目
- **演进意义**：**"无超时保护 = 单点故障放大器"**——一次网络抖动经 rateLimiter 放大成全队列锁死（队头阻塞），5 处 https.request 无一超时是典型的"最初没出问题就一直不补"的历史债；确立双层兜底模式：**调用层 socket 超时（治本）+ 限流器任务级超时（防御）**，后者保证任何 handler 卡死都不会锁死整个队列，rateLimiter 从"无限阻塞"变为"有界等待"。同类多路 I/O 服务（上传/下载/认证）都应照此补超时。

## 2026-09-01 · Dashboard 头像体系：图片磁盘缓存 + user_icon 优先（PR #120，@nixi-agent）

- `#120` (MERGED, 2026-09-01) feat(dashboard): avatar 图片磁盘缓存 + 头像优先 user_icon（569999e，@nixi-agent）

两个独立问题：
1. **头像加载慢**（国内直连 VRChat CDN）：image-proxy 路由扩展磁盘缓存层 `data/img-cache/`（MD5(url) 命名、30 天 TTL、magic bytes 判类型、读序 磁盘→内存→回源→写盘+写内存）；顺手修复 qoder 产物两个运行时 bug：ESM 模块 `__dirname` 未定义导致 web-dashboard 插件加载即崩 + 路径层级 4→5 层
2. **头像显示错**（显示默认机器人而非真实头像，如 XM1023）：根因 `avatar_image_url` 存的是 `currentAvatarImageUrl`（当前穿戴的 3D 模型外观图，穿戴默认模型时即机器人图），`user_icon` 才是资料里设置的真实头像；新增 `avatarOf(iconUrl, modelUrl)` 统一入口（优先 user_icon、兜底模型缩略图），全部头像展示点（friends/feed/friendEvents/实例 owner/实例内玩家/profile/mutualFriends）切换
- auth-guard 豁免 `/api/dashboard/image-proxy` 单一路径鉴权（浏览器 `<img>` 无法带 Authorization header），安全性靠代理自身的 VRChat 域名白名单兜底
- **演进意义**：**"展示数据要区分'正在穿什么'和'用户是什么'"**——currentAvatarImageUrl 是动态穿戴状态、user_icon 是身份头像，混用导致头像失真；确立「图片统一入口」模式：img()/avatarOf/imgProxy 集中到单一工具函数（后续 #122 又抽成共享 core/img-util.js）；磁盘缓存（MD5 命名 + TTL + magic bytes 判型）是 Node 服务低成本的 CDN 加速方案，对国内访问海外 CDN 的场景收益显著。

## 2026-09-01 · Dashboard 轮询瘦身：SSE 富化增量替换全量刷新（PR #122，@nixi-agent）

- `#122` (MERGED, 2026-09-01) perf(dashboard): SSE 增量改造——去掉高频全量轮询（9f411c2，@nixi-agent）

问题：每 10s 拉 /me、每 30s 拉 7 个全量接口（overview/friends/events/events-range/favorites/nicknames-all/me）+ SSE 事件驱动的 refreshFeed/refreshFriends/refreshMeFresh 补拉全量——好友多时网络被高频全量数据轰炸。

改造：SSE 从"触发全量刷新"升级为"推送富化增量"——服务端推送完整渲染数据，前端收到即可增量更新：
- 服务端：新建 `core/img-util.js`（抽出 avatarThumb/avatarOf/imgProxy 共享图片工具，跨模块复用）；event-pipeline `onStoredEvent` DTO 从 6 字段扩到 16 字段（+头像/昵称/状态/平台/信任等级/在线/位置），每事件查 friends 表带 **5s 内存缓存** `_friendCache` 防高频 DB 负载
- 前端：`updateFriendFromEvent()` 好友事件原地更新 state.friends 单个好友（删 refreshFriends 全量拉）；SSE 重连后补一次 load(true) 校准防丢帧；load() 30s → **120s 全量校准**；删 10s refreshMe 定时器
- 实测：35s 窗口轮询 /me 从 10s/次降到 120s/次，全量接口同降到 120s 校准；SSE 富化 DTO 实测带 avatarUrl/status/trustLevel/isOnline/platform
- **演进意义**：**"轮询是最后的手段，增量推送才是正解"**——Web 实时性从"高频全量轮询 + 事件触发全量刷新"升级为"SSE 富化增量 + 低频校准"，网络流量与 DB 负载同步下降；确立 SSE 改造模式：**服务端富化 DTO（一次查库带齐渲染所需）+ 前端原地更新 + 重连校准**；img-util 从 #120 的内嵌函数抽成共享模块，图片处理逻辑开始跨模块收敛（跨 PR 的架构演进）。

## 2026-09-02 · 结构化日志模块 PR #132 + 当日修复集群（#125-#132，@nixi-agent/@psenY/@268500tao）

- `#132` (MERGED, 2026-09-02, @nixi-agent) feat(logging): add production-grade structured logger（2a5a142）——**本次发布主线**

**#132 结构化日志模块**：vrc-monitor 此前**没有日志模块**——日志全靠裸 `console.log`（25+ 文件），Hermes 插件仅把子进程 stdout/stderr 重定向到 `monitor.log` 捕获，非应用自身日志能力。排障只能 grep 一坨 stdout，无法分级、无法轮转、无法按组件定位，且任何输出都可能泄漏 cookie/token/授权码等敏感值。本次新增 `core/logger.js`（**零第三方依赖**，纯 node:fs/path/zlib）：

- **分级输出**：`LEVELS` (debug/info/warn/error/silent)，`VRC_MONITOR_LOGGER_LEVEL`
- **双通道**（stdout 供 Hermes 插件/Docker/systemd 采集 + 文件供本地排障）+ **双格式**（text 人类可读 / json JSONL 供 agent 用 jq 解析），`VRC_MONITOR_LOGGER_FORMAT`
- **日志轮转**：达 `VRC_MONITOR_LOGGER_MAX_SIZE`（默认 10MB）压成 `.gz`，保留 `VRC_MONITOR_LOGGER_MAX_FILES`；命名 `monitor-YYYYMMDD-HHMMSS-<pid>.log.gz`
- **敏感脱敏 `redactSecrets`**：cookie/token/邮箱/密码/IMAP 授权码一律 `[REDACTED]`，覆盖 JSON 引号/Bearer/meta 嵌套/中文授权码/TOTP code 等形态
- **命名子 logger**：`getLogger('<组件>')` 区分 app/ws/api/storage/http/otp/mcp
- **惰性初始化**：`import` 不触发文件 I/O，首访 write() 才 init（消除模块级副作用）

## 2026-09-11 · 网页端在线落库真值：friend-active(platform=web) 清残留世界（PR #181，@psenY，OPEN）
