## 2026-09-01 · rateLimiter 挂死根治：socket 超时 + 队列任务级超时（PR #117）

- `#117` (MERGED, 2026-09-01) fix(api): 加 socket 超时 + 队列任务级超时，防止挂死请求锁死 rateLimiter（64d34ec，@nixi-agent）
- 现象：get_prints 等走 rateLimiter 的 API 工具调用后 420s 超时无响应，但直连 VRChat API 1.7s 秒回；/health 显示 queueLength≈50（上限）且 isProcessing=true 长期不释放
- 根因：vrchat-api.js 的 5 处 https.request（_requestRaw/_basicAuthRequest/_rawRequest/upload/download）均无超时保护——网络抖动时 socket 可永挂不返回也不触发 error；被 rateLimiter 包住的请求占住队头后 `_processing=true` 永不释放，后续所有请求排队干等、集体卡超时
- 修复①治本：5 处 https.request 全部加 `req.setTimeout(REQUEST_TIMEOUT_MS=15000, () => req.destroy(new Error(...)))`——超时 destroy 触发 error → reject，把挂死请求踢出队列
- 修复②防御：core/rate-limiter.js 新增 taskTimeoutMs（默认 30000），_processQueue 内 Promise.race 包住 item.fn()——即使 handler 内部死等也会被强制超时（评审修复 37f795c 进一步做 per-task 超时覆盖 + 聚合 handler 隔离，回应评审 ⚠️1/⚠️2/💡1）
- 关联：issue #118（OPEN，2026-08-31）events 插件启动后自动采集/深挖上千群组持续占满 rateLimiter 队列——#117 修的"挂死锁死队列"与 #118 的"正常请求被大量采集挤占"是同一队列治理问题的两个面，后者仍待处理
- **演进意义**：**"无超时保护 = 单点故障放大器"**——一次网络抖动经 rateLimiter 放大成全队列锁死（队头阻塞），5 处 https.request 无一超时是典型的"最初没出问题就一直不补"的历史债；确立双层兜底模式：**调用层 socket 超时（治本）+ 限流器任务级超时（防御）**，后者保证任何 handler 卡死都不会锁死整个队列，rateLimiter 从"无限阻塞"变为"有界等待"。同类多路 I/O 服务（上传/下载/认证）都应照此补超时。
